# 日程协同

这是通用助手的一项技能，不改变通用助手身份，也不要求创建日程专用实例。

## 先按用户请求选择工具，不默认执行完整协作流程

- 只查看本人已有安排：调用一次 `query_own_schedules`，不调用推荐、找人或协作工具。
- 只寻找或推荐本人空闲时间：调用一次 `recommend_own_candidates`。该工具内部已经读取本人日历，不要再用 `query_own_schedules` 重复核验。
- 同时要求“查看已有安排”和“推荐空闲时间”：两个工具各调用一次。查询工具返回事件明细，推荐工具返回已核实的候选时段，两个结果用途不同；不要将候选时段当作完整事件明细。
- 已给定时间、仅要求创建日程或会议：直接准备确认草稿；不要默认查询、推荐、找人协商。添加参与人时只查找需要的组织成员。
- 只有用户要求询问参与人、协商时间或后台续办时，才进入下面的助手协作流程。本人查询和推荐不需要组织或协作目标。
- 同一轮、同一查询条件的成功结果可复用时，不重复调用。参数校验失败最多按错误提示纠正一次；用户变更范围或出现新的状态后，再按需查询。

### 查询与推荐的入参边界

- `query_own_schedules` 的 `start` 包含起点、`end` 不包含终点，均须为带 `Z` 或明确 UTC offset 的完整时间，间隔大于零且不超过31天。查询北京时间10月22日至26日，应传 `start=2026-10-22T00:00:00+08:00`、`end=2026-10-27T00:00:00+08:00`。
- `recommend_own_candidates` 的 `startDate`、`endDate` 都包含当天，使用 `YYYY-MM-DD`，含首尾最多31个自然日；`timeZone` 用 IANA 名称，例如 `Asia/Shanghai`。同一日期范围应传 `startDate=2026-10-22`、`endDate=2026-10-26`，不能把查询工具的次日排他终点直接作为推荐的结束日期。
- 推荐的 `durationMinutes` 是会议分钟数（5–480）；`dayStart`、`dayEnd` 为指定时区下每天的 `HH:mm`，默认09:00–18:00，结束须晚于开始，会议必须在此窗口内结束。
- `weekdays` 是允许的星期编号：0周日、1周一、…、6周六；省略时仅周一至周五。周末有明确要求时才覆盖默认值，不把“未来三个工作日”理解成任意连续三天。
- 两种工具都只访问当前认证用户的日历，不传其他人的 userId、邮箱或凭据。工具报错说明未知，不能解释为空闲。

## 助手之间的日程协商

日程目标由当前通用助手持续处理，协作请求仅表示一次沟通。一次答复不是整个安排完成的依据。

### 自动办理与恢复

- 多人改期必须先建立 start_collaboration_goal，由该目标联系各参与人的助手、收齐结果、准备改期并等待本人确认。查询本人日历和确认会议身份可在委托前完成；不要在前台另行协商或准备草稿。旧的 coordinate_meeting_times / list_meeting_coordinations 已退出模型工具入口，不用于助手间协作。

- 用户明确要求多人协调或处理冲突、需要后台持续等待时，调用 start_collaboration_goal，将完整目标、时区、日期范围、时长、已确认参与人和可调整范围写入 objective；taskType 使用 scheduling，需要实际安排时 expectedEffect 使用 calendar_write。重试复用 requestKey。
- 成功后由平台受限后台执行继续办理。原会话向用户说明已开始，并展示进度和对话内确认卡片，不要求用户跳转通知入口；不要同时再发相同请求或重复准备日程。
- 用户再次询问进展时，用已返回的 goalId 调用 get_collaboration_goal 获取本会话当前状态；不要仅凭旧聊天中的“等待中”推断，也不要重新创建同一目标。需要本人补充要求时引导使用进度卡的“补充要求并继续”。
- 平台在对方答复、本人确认和写入回执到达时自动唤醒原目标，不依赖浏览器保持打开。接收方在本人身份下执行，复用同一个运行服务，不为每人常驻一个进程。
- 后台每轮从自己的检查点和本人等待事项继续。准备草稿时保留稳定 UUID operationKey，重试复用。不要循环查询等待；调用 checkpoint_collaboration_goal 保存已做事项、尚待条件、下一步和本人的资源编号，然后结束本轮。
- 下游沟通是一问一答的独立请求。同一目标可反复发起新沟通；对方如何处理其内部冲突由对方负责。已发起的子请求和本人草稿尚未结束时，保存检查点等待，不要提前答复或把条件当成实际调整成功。
- finish_collaboration_goal 只用于整个目标已完成时。写入目标必须提交该目标内本人已成功的 draft/meeting/reschedule/cascade 回执。过期、未分享、未知或部分成功都不是完成凭据。不能用历史会议充当本次安排结果。
- 结果未知时保留原操作等待核对，不能换编号再创建。达到预算、授权撤销或需要本人决定时说明实际进度；用户可在原会话进度卡补充要求并继续。

### 冲突与级联改期

- 先查询本人日历和本人组织的会议，明确原安排能否调整及其参会人。按实际冲突独立询问有关助手，可以多轮提出替代时段，不预先枚举协作任务子类型。
- 多个本人组织的会议相互依赖时用 prepare_schedule_cascade，提供每个会议的新时段和依赖步骤；服务端推导占用原时段的依赖，拒绝环形依赖和最终仍重叠的方案。环形换位需要先协商明确的过渡时段。
- 整套方案不可变，展示每步原时间、新时间、依赖和确认链接。本人整体确认后按依赖顺序执行，每步核对账号授权与原会议版本；忙闲查询仅在用户要求协商时执行。
- 某一步等待就保存检查点，完成后自动继续。失败时展示已完成和未完成步骤，不能声称全部失败或已自动撤销。停止仅阻止后续写入；已发出的未知操作必须先核对。
- 恢复原安排必须由本人单独确认补偿方案，按反向依赖顺序执行，并检查原会议版本。外部已变更的会议不能强制覆盖；恢复失败也必须保留真实状态并重新协商。

### 仅在需要助手间协作时使用以下步骤

1. 用 search_collaboration_people（taskType=scheduling）按姓名找人，确认具体人员及其助手 adoptId。重名或同一人多个助手时请用户选择，不猜测 ID，也不要求补充组织体系。
2. 只有需要本人安排明细或候选时间时，才按前面的请求路由选择 query_own_schedules 或 recommend_own_candidates，不默认把两个都调用。用户已经给定时间且只要求询问对方时，不增加本人查询或推荐步骤。别人的日历只能由对方助手在对方身份下查询。
3. 给定候选时段时，在 inputPayload.slots 中提供带明确时区的 start/end（最多6组，范围不超过31天），向各参与人发送相同候选时段，以便对话矩阵逐项展示。服务端只在接收方已授权执行后核验并分享每项忙闲；未答复不等于有冲突。用 send_collaboration_request 联系对方助手，taskType 固定为 scheduling。把问题、具体时段和必要约束放在 taskSummary / inputPayload.query 中；不发送私人日程内容、凭据、聊天或记忆。沿用平台的输入过滤、风险评级和接收方审批。
4. 一次问题与答复构成一个协作请求。网络重试复用原 UUID requestKey；修改时间或再次询问必须生成新的 requestKey。不能把所有沟通绑定成一个长协作，也不要扩展 freebusy、reschedule、cascade 等任务类型。
5. 用 get_collaboration_result 按需读取本助手发出的请求，不循环轮询。pending 表示待主人审批，approved 只表示获批，running 表示执行中，completed 只表示本次沟通有结果。后台目标等待时保存检查点并结束本轮，由平台自动续办。未分享、失败和超时都不能解释为有空。若平台运行服务或协作执行适配器不可用，明确说明等待原因，不声称已唤醒对方或自行绕过原运行链路。
6. 作为接收方，用 list_collaboration_requests 查看发给本助手的任务。pending 请求不能执行或代替主人批准。处理已批准请求时，仅查询本人日历；发送 reply_collaboration_request 的 scheduling 结论，包含 availability、slots、validUntil（最多15分钟）。服务端会在回复 available 时重新查询本人日历。conditional 表示仍有条件未满足；unknown 表示无法确定；答复不代表修改日历或接受会议。
7. 若本人已有安排与提议冲突，可以独立联系相关助手协商新的时间。例如 A 问 B，B 可另外问 C；B 只给 A 本人的结论或替代时间，不向 A 交付与 C 的对话、任务编号或私人日程。A 无需管理 B 的内部协商过程。若无法解决，答复有条件或不可用并继续寻找替代方案。
8. 级联调整中，每个已有会议由其有权的组织者准备改期。所有实际写入仍走已有草稿和本人确认，并检查版本与授权。不能把“愿意调整”“可以协商”当作“已经改好”。已开始的相关调整未完成时保存检查点等待；调整完成后重新查询再答复。若明确放弃调整，可以给出 conditional/unavailable/unknown 的实际结论，后续提议再发起新的沟通。
9. 根据回复继续提议、找替代时间或等待确认。整个目标只有在必要日程写入有成功回执、待确认事项和参与人状态均被明确说明后，才能向用户报告完成。已有对话/工作事项用于保存进度，保留请求和草稿编号以便恢复，不要求请求方持有别人的协作树。

“我的日历”只提供日程增删改查、参与人选择与设置。协作请求、进度和确认操作出现在对话里，后台进度写入持久化对话历史并进入后续上下文，不要求打开日历通知或协作任务页面。

- 日历属于所有用户。个人增删改查无需组织；找人、添加参与人、发起日程协作只能在管理员分配的同一有效组织内进行。没有组织时提示联系管理员开通组织协作权限并分配组织，不得全局搜索或猜测用户编号。
- 用户给出具体时间要求创建日程或会议时，可直接准备日程，无需先查询忙闲或发起协商。用户明确说“不要查，直接创建”时，跳过查询与协商；后续确认与重试也不能重新增加忙闲前置条件。
- 需要查忙闲或协商时才使用 query_own_schedules、recommend_own_candidates或 send_collaboration_request。未知不代表有空；不要把协作答复当作日历已写入。
- search_scheduling_people 查询同组织人员；search_collaboration_people 查询有可用助手的同组织成员。参与人可以没有助手。重名时请用户选择，不猜测 ID。
- prepare_personal_schedule_write 支持 create/update/delete；create/update 可传 participantIds，省略表示保留已有参与人，空数组表示移除全部参与人。参与人邮箱由服务端解析，不传凭据或他人邮箱替代组织成员。
- 会议与日程具有相同创建规则。prepare_meeting_invitation 可直接传 requestKey、event、participantIds；只有用户已经进行候选时间协商时才使用 coordinationId/slotIndex 兼容参数。创建成功无需等待任何参与人的邀请回复。
- 写入工具准备草稿，由用户在当前对话的确认卡片核对后执行；没有成功回执不能报告完成。网络重试复用原草稿和 requestKey/operationKey，不能重复创建。
- 修改或删除使用 query_own_schedules 返回的 resourceId、version；删除还要传准确 title。只允许组织者修改共享日程，不能通过参会人的副本改其他人的安排。重复日程沿用当前底层支持范围，不强行覆盖。
- prepare_meeting_reschedule 修改已记录会议时保留 UID 与参与人，确认后按版本更新原日程，不强制协商，也不要求重新回复邀请。
- query_own_schedules 只读取当前认证用户本人日历，范围不超过31天；时间必须包含明确 UTC offset。allDay 使用日期，结束日不含当天；时区不明确时先澄清。
- 不提供接受、拒绝、暂定等邀请状态管理。底层 CalDAV 可保留其标准参与人字段，但这些字段不作为创建前置条件。
- 不向其他用户分享私人日程标题、地点、聊天、记忆或凭据。当前忙闲结论必须来自查询；读取失败说明未知。
- 用户未指定地点时留空。日历页面直接保存不需要再转到对话确认。
