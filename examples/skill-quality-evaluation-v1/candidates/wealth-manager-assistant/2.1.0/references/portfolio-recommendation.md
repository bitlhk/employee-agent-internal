# 组合诊断与产品推荐 SOP

## 核心原则

产品是组合方案的实现工具，不是方案的起点。

正式推荐遵循：

```text
客户目标
→ 流动性与期限约束
→ 风险金额约束
→ 当前组合问题
→ 目标组合方向
→ eligibleProducts 映射
→ 方案比较与排除说明
```

## 1. 判断是否可以形成正式建议

直接使用 Runtime 返回的授权、客户数据、适当性、产品在售和准入结果。

- `READY`：可以形成正式候选；任务需要比较时可以提供 A/B 方案。
- `DEGRADED`：可以保留已核验的客户分析和配置约束，但不能补造缺失数据、最终比例或具体产品。
- `BLOCKED`：停止正式推荐，说明业务上需要补齐或重新核验的条件。

如果 Runtime 结论与当前事实冲突，停止消费矛盾结果并请求重新核验，不自行改写结论。

`READY` 且已提供客户、持仓、制度和 `eligibleProducts` 时，必须形成正式候选。比例尚待客户确认并不等于候选依据不足；可以不给无依据的精确比例，但不能因此把正式候选降级为泛化方向。

`eligibleProducts`、`excludedProducts`、`Policy`、`Provider`、`MCP`、工具名和状态码只用于内部判断。输出前检查标题、摘要、正文与下一步，把这些内部词替换成“通过适当性校验的当前可售候选”“当前不可选产品及原因”“客户或产品信息暂未完整”等业务语言；不得把内部字段名原样交给财富经理或客户。

## 2. 提炼客户目标

把目标写成可检验的约束，不使用“稳健增值”“收益尽量高”一类空泛表达。

优先明确：

- 已知资金用途及最早使用时间；
- 必须保留的流动性；
- 投资期限；
- 可以承受的损失金额和行为反应；
- 现金流、资本保全、长期增值等目标的优先级；
- 当前持仓中不能或不宜调整的部分。

## 3. 建立流动性底线

只使用平台提供或客户已确认的计算依据。

已知金额和日期完整时，可以说明：

```text
已知现金需求
+ 平台认可的安全储备
- 已有可用流动资产
= 待补流动性缺口
```

具体公式、储备月份、比例和金额必须来自当前机构规则或确定性计算。缺少依据时，只说明需要保护的资金用途和期限，不自行生成百分比。

只有当前事实证明可以在需要时及时、低成本赎回或支取的资产，才能计入流动性底线。封闭期、锁定期或提前赎回受限的产品不得因为风险较低就称为“高流动性”，也不得用于满足流动性底线；`323` 天封闭产品应归入期限受限的稳健层，而不是流动层。

## 4. 区分风险能力、风险意愿与风险体验

- 风险承受能力：Runtime 的有效评估结论；
- 风险意愿：客户愿意主动承担多少不确定性；
- 风险体验：客户面对具体金额回撤时可能采取什么行为。

客户等级允许某类产品，不代表组合应配置到上限。资产规模较大也不代表客户愿意接受较大金额回撤。

## 5. 诊断当前组合

只分析已有事实支持的维度：

- 流动性是否覆盖已知用途；
- 到期结构是否与资金时间表匹配；
- 单一产品、资产类别、发行人或风险来源是否集中；
- 当前组合风险是否与客户真实行为承受能力一致；
- 现有产品的期限、费用和退出条件是否影响调整；
- 调整后相较当前组合解决了什么问题。

没有完整持仓时，输出“可确认的局部问题”和“尚不能判断的维度”，不要生成完整组合结论。

正式推荐必须明确写出“当前持仓诊断”。即使当前无在持产品，也要说明“当前无在持产品、待配置资金是多少”，再解释候选如何改变现状。

## 6. 形成目标组合方向

先描述每一部分资金承担的任务，再讨论产品：

```text
流动层：覆盖明确现金需求和必要储备
稳健层：承担中期目标并控制波动
增值层：使用长期不用且可承受波动的资金
```

三层只是分析框架，不是固定比例。根据客户事实可以合并、拆分或不用该框架。

## 7. 映射产品

正式候选必须来自 `eligibleProducts`。

对每个候选说明：

- 对应哪个组合目标或缺口；
- 产品风险、期限、流动性、费用和起购要求；
- 与客户期限、流动性和风险体验的匹配；
- 对当前集中度的影响；
- 仍需客户确认的风险或取舍。

可以引用 `excludedProducts` 解释为什么不选，但要明确不可推荐。不要把搜索结果、历史产品或停售产品包装成备选。

## 8. 条件性 A/B 方案

只有信息完整且比较有助于客户决策时才生成两套方案。

如果 Runtime 已提供确定性的可投资总额、流动性底线、产品角色和 A/B 配置约束，必须使用这些事实形成两套金额闭合的方案：每套合计等于可投资总额，流动性工具达到最低金额，期限受限产品不得计入流动性底线。不得因为“比例需要确认”退回泛化方向。

- 方案 A：优先满足更高等级的刚性目标，例如流动性和较低波动；
- 方案 B：在同样守住刚性约束的前提下，承担更多波动以换取长期增值机会。

每套方案都必须说明：

- 相同的刚性约束；
- 不同的取舍；
- 使用的正式候选；
- 主要风险和不适用条件；
- 需要客户确认的事项。

任何建立在错误期限、流动性或产品可用性判断上的方案都不可执行；金额和比例再具体，也不能把这类方案描述为“可直接落地”。

如果没有计算依据，不给精确比例；可以给条件性方向，例如“确认该资金三年以上不用后，再讨论增值层规模”。

## 9. 正向推荐输出

```text
客户目标与核心约束

当前组合诊断
- 已确认问题
- 尚缺信息

目标组合方向
- 每部分资金承担的任务
- 比例或金额的计算依据（如有）

方案 A / 方案 B（条件满足时）
- 配置逻辑
- 正式候选及产品事实
- 主要取舍

排除项
- 产品
- 不可推荐原因

风险、费用与流动性

客户沟通建议

下一步
```

正向推荐本身是只读分析，不生成确认卡。只有用户明确要求创建跟进、保存方案或执行交易时，才交由平台进入写操作确认。

## 10. 产品资料分析与对比

用户只询问产品资料时，可以使用只读产品事实进行分析，不产生客户适配结论。

产品对比应保持同一数据时点，只比较都有依据的风险、期限、流动性、费用、策略和历史表现。没有数据的维度标记缺失，不使用固定权重或星级评分补齐。

一旦用户要求“给这个客户选哪个”，必须进入正式候选流程。

## 自检

- 是否先挑产品，再反向拼客户理由？
- 是否把风险等级允许误写成建议高仓位持有？
- 是否出现没有计算依据的精确比例或金额？
- 是否解释了未选产品及原因？
- 是否把历史表现写成未来收益预期？
- 是否给出了客户可以理解的主要取舍？
